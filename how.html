How this was made
Play the game · Read it · The spec

A game, built out loud.

A student asked how are video games made? The answer is one HTML file you can open from disk. This page is the time-lapse of how that file got written — by a teacher and a few long-running AI agents, in about thirty hours on 1 and 2 September 2026.

Third pass. Times are Hawaiʻi time, from git. The dialogue is summarized, not a transcript. The X-ray phases have their close-ups; the other phases are still waiting for theirs. Close-ups are folded; click one to open it.

The whole story, ADEPT-style

ADEPT is a way to explain a hard thing: Analogy, Diagram, Example, Plain English, then Technical. We use it here because this page is for you, not for the agents who typed the file.

Analogy
First someone wrote the recipe. Then a cook followed it, one bowl at a time, until there was dinner. Then other cooks cut a window in the kitchen wall so you could watch the stove. Then they kept rewriting the sign next to the window until a first-time visitor could follow what the stove was doing.
Diagram
Two pictures matter. The game is a factory line. The build is a short timeline. They are the same idea at two speeds.
Example
Open the game. Press X. Hold an arrow key. The rows light from the top down. That light is what every phase below was trying to make visible.
Plain English
A teacher wrote strict rules. An agent built a walkable world overnight. Other agents added a panel that shows the rules happening live, then rewrote the panel until it stopped lying to a first-time reader. Someone else pointed the classroom URL at the game. Then this page got written, and the people who cut the window came back to fill in their part of it.
Technical
game.html · 1,800 lines · ten numbered sections plus an optional eleventh · no build, no dependencies · PRs #2 through #8.

The two pictures

The file is one sentence, sixty times a second. Only the middle of it is allowed to change the world.

The build is that sentence, stretched across a day and a half. Each box below is a phase. Times are Hawaiʻi time, because that is where the classroom is, and each one is when that piece landed on the main branch.

Thirty hours, not three days. The first draft of this page said three, because agents stamp their commits in UTC and Hawaiʻi is ten hours behind, so an evening here reads as the next morning in the log. Worth knowing the first time you read a git history.

Phase 0 · Sep 1, 3:40pm

Someone writes the recipe first

A teacher wrote the rules before any agent wrote code. Readers first, players second.

Before any agent typed a game, a teacher wrote the rules. That file is PRD.md. The first line that settles every later argument:

The user is a 15-year-old reading the source, not a player.

Why that line exists: a fun game with clever code would hide the lesson. A slightly duller game you can trace in fifteen minutes is the whole point.

  • One file. No build. No internet. Microsoft Edge and Chrome.
  • Ten numbered sections, in a fixed order. Render never writes.
  • Four deliverables together: the game, a teardown, ten edits, a twelve-line README.
  • Stop at P1. Combat and sound are listed so nobody "helpfully" adds them.

Why: agents wander without a spine. The overnight build was told to follow section 9 of that file, in order, and commit after each step.

Phase 1 · Sep 1, about 4:00pm · PR #1

Does a blank browser even do this?

A short test proved Chrome could run the game's basics before any game code existed.

The game did not exist yet. A short agent session checked the kitchen: Chrome 148 was installed, and a throwaway page in /tmp proved Canvas, keys, a game loop, and save/load all work from file://.

One heads-up they left for the next session: Chrome DevTools paints a red "unsafe file URL" line on every local page. That is the browser talking to itself, not a bug in the game.

Tested: a six-check smoke page, movement and save/load on screen. Nothing from that page was kept — it was not a deliverable.

Phase 2 · Sep 1 evening, merged 10:32pm · PR #2

Overnight: dinner, one bowl at a time

One agent followed the spec step by step overnight and built the whole playable game.

This is the first of the three long threads. A Cursor cloud agent was pointed at the spec and told to stop at P1. It built game.html in the listed order, committing after each step — except steps 5 and 6, which are the same idea (giving an item is flipping a quest flag), so they landed together. 

1  empty file, ten banners
2  CONFIG + DATA + STATE     the world as text, nothing moving
3  LOOP + RENDER             a still map on screen
4  INPUT + UPDATE + COLLIDE  you walk; trees stop you
5+6  people, items, quests   talk, pick up, open a bridge
7  a second map              a cave, through a door
8  SAVE                      K, L, N, a "saved" notice
9  prove RENDER is pure      plus a student-proof read-through
10 TEARDOWN, CHANGE-ME, README   written against the finished file

Extra things they added because a reader would trip: a file map at the top, sandy trails to each outdoor item, and boot-time checks that name a mistyped map row instead of failing silently.

Tested: 1,222 lines, no line over 100 characters, no banned string, all ten banners, a real-Chrome playthrough of three quests / both maps / save / reload in 35 seconds. Edge was not on the machine. Still isn't, as of this draft.

Phase 3 · Sep 2, about 2:00am · PR #3

Cut a window in the kitchen wall

A bolt-on panel now shows the game's rules running live, without changing the game itself.

Playing the game still hid the lesson. The second thread starts here: an optional eleventh section, opened with X, that shows the factory line live. What it shows:

  • Intents
  • A log of what just changed
  • The tile you face
  • The whole of state
  • The heartbeat

The important constraint, said out loud: delete section 11, the side panel, and a few lines in the loop, and the game is exactly the same. The window is bolted on. It is not the house.

Why: a student should see the pipe while walking, not only by reading.

Tested: the same mechanical checks, plus a run by a headless browser (one with no window, driven by a script). The reading-guide line numbers had to be refreshed — a new section shoves every later line down.

Close-up · the whole hook is two snapshots

The window needed a way to know what UPDATE changed, without touching UPDATE. The trick: the game already turned state into a string once a frame, right before drawing, to prove that drawing changed nothing. The X-ray takes one more string, right before the rules run, and compares the two. 

one turn of the loop

  snapshot A = JSON.stringify(state)      before UPDATE runs        (new)
      │
      │   UPDATE runs: none, one, or several times
      ▼
  snapshot B = JSON.stringify(state)      before RENDER runs        (already there)
      │
      │   RENDER runs
      ▼
  compare state against B                 different? the game stops (already there)

  A against B    = everything UPDATE changed   →  the panel's "what changed" box
  B against now  = everything RENDER changed   →  must always be nothing

Nothing inside the rules is instrumented. The same string that proves drawing is honest is also the complete record of what the rules did. If you had wanted that record, you would have had to take those two snapshots anyway.

Close-up · one line that got un-clevered

The first draft of the diff merged the keys of the two snapshots with a compact idiom — one line, and a good one on most projects. It was rewritten the same night as a plain loop over each object's keys, four dull lines. Not because the line was wrong. The rule for this repo says a fifteen-year-old has to trace the file, and a clever line costs them a minute the game does not get back.

X-RAY: boring key-union loop instead of Set spread; show whole state at once — a commit message inside pull request #3
Close-up · the bolt-on promise, in the file's own words
Delete this section, the <aside> at the top, and the four LOOP lines that call it: same game. — the section 11 banner in game.html (it said three lines that night; pause made it four)

Note: the new section pushed every later line down by sixty to a hundred, and 55 line numbers in the two reading guides went stale at once. A small checker for those citations was written the same night, and it has caught drift on every phase since.

Phase 4 · Sep 2, 8:50am · PR #4

Freeze one heartbeat

P freezes the world, . runs one update, and paused time is thrown away on purpose.

Sixty frames a second is too fast to watch. So:

  • P — freezes the world (drawing keeps going).
  • . — runs exactly one update.
  • Resume — does not fast-forward through a pile of leftover time. The clock throws those seconds away on purpose.

Pause is not saved. Only "is the panel open?" survives a reload. Hide the panel and the world starts again, so a frozen game can never sit there with no explanation.

Staffing: a stronger model wrote the spec and judged; a cheaper model typed; the session re-ran the tools before each commit. That pattern repeats in the rest of this thread.

Close-up · why pause throws time away

The loop keeps a small bank of unspent time. Each frame adds what passed since the last one, then runs UPDATE once per sixtieth of a second it can afford. Pause is one question asked of that bank, before the spending starts:

The whole decision is five lines in section 11. The reason it throws time away instead of saving it: if paused frames kept filling the bank, ten seconds of pause would be six hundred updates owed, and the game would run all of them in the one frame after you resume. You would teleport. Drawing never pauses, which is why the picture stays on screen while the world holds still.

Note: also why P and . do nothing unless the panel is open, and why hiding the panel un-pauses: the panel is the only place that says PAUSED. No explanation on screen, no pause.

Phase 5 · Sep 2, 9:10am to 1:45pm · docs, then PR #5

The window has to explain itself

The panel gained a live diagram, captions, and copy buttons, so it teaches instead of just showing.

  • 9:10am, the guide fix — a user test found the gap: the panel existed, but the student guide never mentioned it. Someone could do all six reads and never press X. The guides got a "before you start" pointer, and the README grew the new keys. The game file itself was not touched.
  • Proof the window unbolts — a tool strips section 11 from a copy and plays the leftover game. A robot was taught to press X, P, and ., so those rules stay true after the next edit.
  • v1.3: the panel explains itself — by late morning the panel was accurate and terse, and that was the problem: a student who did not already know the arrow could not learn it from five boxes of field names. v1.3 adds a seven-row live diagram, a one-line caption under each box, and two buttons that copy this exact moment into a question for any AI. The panel also learned to scroll itself so a school laptop does not lose the game off the bottom of the screen.

Tested: four tools, all green. Playthrough 36 checks, 28 seconds, zero console lines, run three times. After stripping the X-ray, the leftover game was still 1,243 lines — byte-identical to before this evening. That is the real proof the new words stayed inside the window. Budget warning they left: 1,798 of 1,800 target lines. Anything else has to pay for itself.

Close-up · the seven rows, mid-step

Hold the right arrow with the panel open and the top box reads like this. A filled marker means that stage did something on the frame you are looking at; a bar means it sat still. Both signals say the same thing, so it reads on a projector where the gold blurs into the grey. 

▶ keyboard    last key you pressed: arrowright
▶ 4 · INPUT   writing that down in intents
▶ intents     moveRight
▶ 5 · UPDATE  updates this frame: 1
│ 3 · state   timers only, last #812 player.tileX 5 → 6
▶ 7 · RENDER  frame 812 drawn, state untouched
▶ screen      what you are looking at

Note: one rule kept the diagram honest: it computes nothing. Every word on it is a value one of the five boxes below already shows, said shorter. (The state row's wording is from phase 7; that day it said less.)

Close-up · a test that could not fail

The copy buttons use the one clipboard call that behaves the same from a double-clicked file in Edge and in Chrome. If the browser refuses, the text stays selected for Ctrl+C. The robot test for it was first written to click the button from inside the page, by script. It passed. It was also worthless: a script clicking is not a person clicking, and the clipboard only obeys a person. The check was rewritten to press the button through the browser, the way a hand does, and only then did a pass mean anything.

Close-up · seven numbers that were off by one

Adding the diagram put 74 lines above the script, so every line number in both reading guides shifted by 74. The shift was applied by arithmetic, then read back by hand. Reading it back found something older: seven numbers written in prose, where the automatic checker never looked, had each been off by one since the build. One was the map row a student is told to edit first. Each would have sent someone to the wrong line and let them think they had misread the code.

Note: measured, not guessed: before the panel learned to scroll itself, a school laptop at 1366×650 had to scroll the page 1,300 pixels to see the whole panel, with the game sliding off the top. After: 678.

Phase 6 · Sep 2, 2:20pm · PR #6

The classroom door was already open

The school link already worked. It just needed to point at the game, not the README.

Third thread, separate from the X-ray work.

  • The problem — the GitHub Pages URL was already publishing the repo. It rendered the README — "download and double-click" — and never mentioned that game.html was sitting right there, playable. That is why it felt like the game was not on the web.
  • The fix — a tiny index.html that redirects to the game. The README's first link becomes "play it here." The spec adds one sentence: Pages is extra, not instead. The file on disk still opens with the network off.

Tested: walked the live root after merge; it opened the game; Chrome console empty. They could not set the GitHub "homepage" field from that session (permission denied). Edge on a school laptop is still on the to-do list.

Phase 7 · Sep 2, 4:30pm · PR #7

Five sentences that were lying

Two readers who never compared notes tripped on the same two sentences. Five got fixed.

Back in the X-ray thread. A second look — screenshots at school resolution, one reader pretending to be fifteen, one reading as a learning-UX reviewer, none of them sharing notes. The top two findings matched. Those two were treated as certain.

  • After P, the keyboard row said you pressed p, as if that key went down the pipe. It does not. The game never sees it.
  • UPDATE lit up while the state row said nothing changed. Between steps, only two timers move, and the log hides them on purpose. The row now says "timers only."
  • An empty prompt box ate the first screenful. Hidden until you copy something.
  • A caption claimed nothing lives outside state, under a box that is visibly not state.
  • The diagram was a readout. It is now an invitation: hold an arrow, watch the rows light.

Eighteen lines went in. Eighteen comment lines came out. The file is exactly 1,800 lines, and no student-facing line number in the guides had to move.

Tested: 44 playthrough checks, 29 seconds, twice, zero console output. Still nobody has opened this in Edge. The new thing to eyeball there: the widest diagram row is 54 characters, and a fat scrollbar plus Courier New might clip it.

Close-up · why two readers who do not talk

One reader was told to be fifteen. One was told to be someone who reviews learning software. Neither saw the other's notes, and neither saw the notes from the screenshot pass. If two strangers trip over the same sentence unprompted, that is evidence about the sentence, not about the readers. Agreement was the bar for "certain." The other three findings were judgement calls and are labelled that way in the spec.

Close-up · the top finding, before and after 
after pressing P

  before   │ keyboard    last key you pressed: p
           │ 4 · INPUT   nothing to write down       ← reads as: p went in and vanished

  after    │ keyboard    p — not a game key, INPUT skips it
           │ 4 · INPUT   nothing to write down       ← reads as: INPUT never heard it

Same markers, same facts. Six words changed, and the panel stopped teaching that every key goes down the pipe. The decision uses the game's own list of keys it listens for, so the panel cannot drift from INPUT if that list ever changes.

Close-up · three tenses for one row

The state row had two states and needed three. "This frame:" when a real change just landed in the log. "Timers only, last …" when the rules ran and moved two per-step timers the log skips on purpose, which is most frames while walking. "No change, last …" when nothing at all moved, which is every paused frame. The difference between the last two is one comparison: did snapshot A differ from snapshot B at all. That comparison already existed.

Close-up · two things they said no to
  • Rewording the UPDATE row on the single frame a . step runs. That frame lasts sixteen milliseconds. Nobody can read it, and the state row plus the log already show the step afterwards.
  • Putting the five detail boxes in file order, 3-4-5-6-7. It would separate UPDATE from the COLLIDE box that explains why UPDATE let you step or not. The arrow's order won; the caption explains the numbers instead.

Note: a smaller honesty note from the same pass: after stripping the window, the leftover game is 1,242 lines now, one fewer than phase 5 quoted, because one trimmed comment sat outside the window. So the earlier "byte-identical" claim stopped being true, and the handoff says so rather than letting it stand.

Phase 8 · Sep 2, 9:30pm · PR #8, then a second pass

The time-lapse itself

A Cursor agent wrote this page in one evening. The X-ray thread then fixed its clock: thirty hours, not three days.

  • The first draft — a Cursor agent wrote the ADEPT frame, the three threads, the phases, and a note under each one saying what a later session should add, all in one evening session. It linked the page from the help line under the game canvas without moving a single line number in the reading guide.
  • The fill-in, same night — the X-ray thread came back and filled in phases 3, 4, 5 and 7, the ones it had lived through, from its own handoff notes, commit messages and the code. It also fixed the clock: the first draft read agent timestamps as local time and said three days. It was thirty hours.

Tested: this page was opened in headless Chromium at 1366×650 before and after, checked for horizontal overflow and console output, and the maintainer tools were re-run to show game.html did not change. Nobody has opened any of this in Edge yet.

How they knew it worked

Agents do not get a gold star for typing. They have to show the work. Four small Node scripts live in tools/. They are for maintainers, not for you — the spec refuses a test suite as a student deliverable. Still worth knowing they exist:

The five-minute playthrough the spec asked for came in around half a minute, every time they timed it.

Honest gap, repeated in every handoff: this file has not been opened in Microsoft Edge on a managed school laptop. That is the next human test, not the next agent task.
